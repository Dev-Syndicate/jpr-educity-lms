Database Schema

Seven tables in PostgreSQL (Supabase), with the constraints that make the borrowing rules impossible to break — including from outside the application.

Entity relationships

Every arrow is a foreign key, pointing from the child toward the parent it references. The labels say what the relationship means, not merely that one exists.

How a loan moves through its states

A loan has no status column. Its state is derived from three fields, so it can never disagree with itself.

Why renewal is blocked while a fine is unpaid Renewal sets the due date to today + 15 days. If an overdue book could be renewed freely, the new due date would sit in the future and the days already owed would silently disappear. Requiring payment first keeps the arithmetic honest without needing a carry-forward mechanism.

How an account becomes able to borrow

Two routes in, one gate. A librarian's judgement is the only thing that turns an account into one that can walk out with a book.

Approval happens at the counter, not in a queue A pending account waits indefinitely at no cost. It is approved the first time the person turns up with a book, when the librarian can check a college ID against the declared details and approve-and-issue in a single action. Registrations from people who never borrow simply stay pending — there is no backlog to clear, and nobody has to verify a stranger from a form alone.
The declared member type is a claim, not a fact An applicant chooses “student” or “faculty” on the form, and that choice decides whether they may hold 3 books or 5. It takes effect only on approval — the librarian must confirm it alongside the roll number, and can correct it before approving.

Why an audit table earns its keep Cash changes hands at the counter, and “I did return that book” disputes are routine in a college library. loan_events is append-only and cheap to write, so every issue, return, renewal, payment and waiver leaves a permanent record of who did it and when.

The constraints that enforce the rules

These live in the database rather than the application, so they hold even if someone bypasses the interface entirely and calls the API directly.

A copy can only be lent once at a time

create unique index loans_one_active_per_copy
  on public.loans (copy_id)
  where returned_at is null;

A partial index over open loans only. Two librarians scanning the same barcode simultaneously cannot both succeed — the loser gets a unique-violation, which the issue function turns into a readable message. There is no read-then-write gap for a race to slip through.

Members cannot promote themselves

Two independent mechanisms, because one of them could be loosened by a careless future edit:

  • Row-level security grants members no UPDATE policy at all on profiles.
  • A BEFORE UPDATE trigger rejects any change to role, member_type, roll_number or is_active from a non-librarian — and fires regardless of what the policies say.

There is exactly one place where a non-librarian legitimately writes those columns: register_member(), which stamps a new applicant as a pending member. The trigger cannot simply be skipped for SECURITY DEFINER callers — auth.uid() is a request-level setting that persists into a definer function, so the applicant still looks like themselves from inside it. Instead register_member() sets a transaction-local flag that the trigger honours:

perform set_config('app.privileged_write', 'on', true);  -- true = this txn only

The flag is not a hole an attacker can climb through: set_config is reachable from SQL, but a member has no UPDATE policy on profiles, so RLS refuses the write before the trigger is ever consulted. The flag only relaxes the second of the two barriers, and only inside the transaction that set it.

Dates are Indian, not UTC

Supabase servers run in UTC. Between midnight and 05:30 IST, current_date still reports yesterday in India — which would undercount a day of fine and could record a morning return as having happened the day before. Every date calculation goes through one function instead:

create function public.today_ist() returns date
language sql stable as $$
  select (now() at time zone 'Asia/Kolkata')::date;
$$;

Faculty borrow for a term, students for a fortnight

The loan period depends on who is borrowing: 15 days for a student, 90 days for faculty. A student's book circulates among a cohort that needs it back; a faculty member keeps a reference text for the length of a course.

Two columns rather than a lookup table, matching max_books_student / max_books_staff — member_type is a two-value enum, so a table of two rows would be indirection without benefit. Both are editable in Settings.

The rule lives in issue_book() and renew_loan(), which pick the column from the borrower's member_type. Nothing is decided in the UI, so a direct API call gets the same period.

Fines are unchanged: a faculty loan accrues the same ₹1/day once its 90 days are up. And because every loan snapshots loan_period_days_at_issue, changing either figure never moves a due date already set.

Member photos are private, and the database stores a path

Photos live in a private Supabase Storage bucket called member-photos, one object per member at <member-uuid>.<ext>. A member's photo is personal data: it identifies a real person at a real institution, so a public bucket would put every student's face on the open internet for anyone who guessed a URL.

profiles.photo_path holds the object path, never a URL. A stored URL would either be public (defeating the bucket) or a signed URL that expires — leaving dead links in the database. The path is durable; the application mints a short-lived signed URL when it renders the image.

The bucket's own RLS policies decide access, and they mirror the table's: a librarian may read and write any member's photo, because verifying a face against a card is a counter task; a member may read only their own and cannot write at all, since members are read-only everywhere else in this system. Naming objects by the member's uuid is what makes those policies expressible — the owning member is derivable from the filename, so a policy can compare it to auth.uid().

Uploads are constrained at the bucket, not just in the form: 2 MB and image MIME types only. A form check is a convenience; the bucket is the boundary.

A shelf address is three parts, not one string

The racks are labelled Row 09 → Rack-01 → Section-A, so a copy's location is stored the same way: row_no, rack_no and section, replacing the old free-text shelf_location.

Three columns rather than one string because the parts are asked about separately. "Everything in Row 09" and "what is in Rack-01" are ordinary questions, and they are an indexed equality test on structured columns versus a like against whatever format someone happened to type. A single field also drifts — 09-01-A, R9/R1/A, Row 9 Rack 1 all mean the same shelf and none of them sort.

All three are optional and free text, bounded to 20 characters. A copy can be catalogued before it is shelved, and the labels are not always numeric — trailing letters like 09A occur. They are stored uppercased and trimmed so a and A cannot become two sections.

Existing shelf_location values were preserved, not parsed: each moved into section verbatim. Splitting A-01 into a rack and a section would have been guesswork about a format that was never enforced, and a wrong guess silently sends a librarian to the wrong shelf. Re-entering a handful of locations is cheap; discovering they are quietly wrong is not.

Category is what it is; department is where it belongs

These answer different questions and used to be conflated in one free-text category column that held values like "Computer Science" — a department, not a category.

  • category — what kind of item this is: book, non_book_material, project, thesis, proceeding, magazine. A fixed enum, because the list is a library-wide classification that should not grow by typo. Adding a kind is a migration, deliberately.
  • department — which department owns the title: "S & H", "CSE", "MECH". Free text, because it follows however the racks are actually labelled and varies between campuses.

Existing rows were migrated by moving the old free-text value into department and defaulting category to book — the previous column only ever held subject names, so nothing is lost and nothing is guessed.

department joins the full-text search_vector at weight D, so "S & H" is searchable alongside title and author. category is not in the vector: casting an enum to text is only stable, never immutable, and a generated column rejects it. It needs no free-text search anyway — a closed six-value list is filtered with a dropdown and an indexed equality test.

Not to be confused with profiles.department, which is the member's department. The two are unrelated: a CSE student borrows from the S&H racks all the time.

Anonymous callers cannot reach the librarian RPCs

Every privileged function already begins with assert_librarian(), so an anonymous call fails with "You must be signed in to do this." even though PostgreSQL grants EXECUTE to public by default. That is the real boundary and it holds.

The default grant is still revoked, for two reasons: Supabase's own security advisor flags every SECURITY DEFINER function reachable by anon, and a future function whose author forgets the assert_librarian() line should fail closed rather than open. register_member() is the deliberate exception — self-registration has to be callable before sign-in.

The signed-in user is fetched in one round trip

Every page needs two things before it can render: proof the token is valid, and the caller's profile row. Asking for them in sequence costs two network round trips, which on a deployment where the application and the database sit in different regions is the single largest component of a page load.

They cannot be run in parallel naively, because the profile query needs an id and the id comes from verifying the token. current_profile() removes that dependency by resolving auth.uid() inside the database instead:

create function public.current_profile() returns public.profiles
language sql stable security definer as $$
  select * from public.profiles where id = auth.uid();
$$;

The application now issues getUser() and current_profile() concurrently and waits for the slower of the two. It still refuses to trust the profile until getUser() has come back verified, and it re-checks that the returned row's id matches the verified user — the RPC is a latency optimisation, never an authentication step.

A plain select … where id = <uid> could not replace this. A librarian's RLS policy lets them read every profile, so the filter is what confines the query to their own row; the whole point of the function is to supply that filter without a prior round trip to learn the id.

History cannot be re-priced

Each loan stores loan_period_days_at_issue and fine_per_day_at_issue when it is created. Raising the fine to ₹2/day next term changes what new loans accrue, and leaves every past fine exactly as it was assessed. A fine's amount is null while it is still growing and frozen the moment the book comes back.

A fine cannot be both paid and waived

Check constraints keep the settlement columns coherent: paying requires paid_at and collected_by together; waiving requires waived_at and waived_by; neither can be recorded against an amount that was never assessed.
